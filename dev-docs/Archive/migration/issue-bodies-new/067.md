## Problem

The two-axis taxonomy (16 Subjects × 12 Photo Types) already gives every image **two independent labels** — one Subject, one Photo Type — which resolves the obvious cross-genre cases that motivated the original multi-genre proposal:

- Wildlife portrait → Subject=`wildlife`, Type=`portrait`
- Street landscape → Subject=`cityscape`, Type=`street` (or Type=`landscape`)
- Architectural landscape → Subject=`building`, Type=`landscape`
- Event documentation → Subject=`people`, Type=`documentary`

However, **each individual axis is still single-label** (argmax over its distribution). Real images legitimately occupy multiple positions on the same axis:

- **Subject ambiguity**: a person walking a dog (`person` + `pet`); a child at a landmark (`child` + `building`); a still-life with flowers (`object` + `plant`)
- **Type ambiguity**: an environmental portrait (`portrait` + `landscape`); a long-exposure cityscape at night (`long-exposure` + `architecture` + `night-sky`); a candid street shot (`candid` + `street`)

Single-label-per-axis behavior:
- Discards the full per-axis distribution that `genre_router.py` already computes
- Forces the Stage 6 **region router** (driven by Subject) to choose one routing path even when two would apply (e.g. skip eye-sharpness on a `person` + `pet` image)
- Forces the **aesthetic weighter** (driven by Photo Type) to pull a single weight vector when a blended vector would better reflect the image
- Reduces flexibility for Darktable tag-based curation — users see one Subject tag and one Type tag, not the secondary candidates the model already considered

## Proposed Solution

Promote **each axis independently** to multi-label, keeping Subject and Photo Type fully decoupled per the Stage 6 contract:

1. **Router Output** — `GenreResult` already carries full Subject and Photo Type distributions. Add per-axis top-N lists alongside the existing argmax fields:
   ```python
   @dataclass
   class GenreResult:
       subject: str                              # argmax — kept for backward compat
       photo_type: str                           # argmax — kept for backward compat
       subject_confidence: float
       photo_type_confidence: float
       top_subjects: list[tuple[str, float]]    # NEW: top-N per axis
       top_photo_types: list[tuple[str, float]] # NEW: top-N per axis
       subject_distribution: dict[str, float]   # unchanged
       photo_type_distribution: dict[str, float]
   ```

2. **Stage 6 Region Router** — When `top_subjects` contains multiple entries above floor, the region router runs sub-scores for **each qualifying Subject** and blends results by confidence. E.g. a `person (0.62) + pet (0.38)` image runs both eye-sharpness (person path) and animal-eye detection (pet path), then blends sub-scores at 0.62 / 0.38.

3. **Stage 6 Aesthetic Weighter** — Blend per-Type weight vectors from the `aesthetic_weights` SQLite table:
   ```python
   total = sum(c for _, c in top_photo_types)
   blended_weights = {}
   for type_label, conf in top_photo_types:
       w = aesthetic_weights[type_label]
       for k, v in w.items():
           blended_weights[k] = blended_weights.get(k, 0) + (conf / total) * v
   ```
   Master score remains `min(technical, aesthetic)` — only the aesthetic vector becomes a confidence-weighted blend.

4. **Database Schema** — Two JSON columns, one per axis. Keep the existing scalar columns as the highest-confidence label for fast filtering:
   ```sql
   ALTER TABLE photos ADD COLUMN subjects TEXT DEFAULT '';     -- JSON: [{"label": "person", "confidence": 0.62}, ...]
   ALTER TABLE photos ADD COLUMN photo_types TEXT DEFAULT '';  -- JSON: [{"label": "portrait", "confidence": 0.71}, ...]
   -- existing scalar `subject` and `photo_type` columns are the argmax — preserved
   ```

5. **Darktable Bridge** — Extend the hierarchical tag namespaces already in place (`photon|subject|*`, `photon|type|*`) to write **all top-N labels per axis**, not just the argmax. The Lua applicator already supports hierarchical tags from the two-axis commit — only the writer side changes. XMP gains two sibling sequences:
   ```xml
   <photon:Subjects>
     <rdf:Seq>
       <rdf:li photon:Label="person" photon:Confidence="0.62"/>
       <rdf:li photon:Label="pet"    photon:Confidence="0.38"/>
     </rdf:Seq>
   </photon:Subjects>
   <photon:PhotoTypes>
     <rdf:Seq>
       <rdf:li photon:Label="portrait"  photon:Confidence="0.71"/>
       <rdf:li photon:Label="candid"    photon:Confidence="0.22"/>
     </rdf:Seq>
   </photon:PhotoTypes>
   ```

6. **UI Visualization** — In Darktable users see two independent tag stacks:
   - `photon|subject|person`, `photon|subject|pet`
   - `photon|type|portrait`, `photon|type|candid`
   - Removing a tag from either axis feeds the [back-training pipeline](#66) as a per-axis correction signal — Subject corrections do not perturb Photo Type prototypes and vice versa.

## Selection Strategy

**Recommendation: hybrid top-K with floor, applied independently per axis.**

```python
def select_labels(distribution: dict[str, float],
                  top_k: int = 3,
                  floor: float = 0.15) -> list[tuple[str, float]]:
    candidates = {lbl: p for lbl, p in distribution.items() if p >= floor}
    return sorted(candidates.items(), key=lambda x: -x[1])[:top_k]

top_subjects   = select_labels(subject_distribution,    top_k=3, floor=0.15)
top_photo_types = select_labels(photo_type_distribution, top_k=3, floor=0.15)
```

Floor of 0.15 sits below the 0.45 routing confidence threshold but above CLIP noise. Per-axis selection means a high-confidence Subject (single label) can coexist with an ambiguous Photo Type (3 labels) on the same image, which matches how real photos sit on the two axes.

## Stage 6 Alignment

This change is a **prerequisite for the Stage 6 modular scoring pipeline** described in `dev-docs/architecture/scoring-module-contracts.md`:

- The `region_router` contract assumes Subject can be a multi-label input
- The `aesthetic_weighter` contract assumes Photo Type can be a multi-label input
- `FusionResult.as_flat_dict()` must surface the argmax of each axis to preserve backward compatibility for `pipeline.py`, `darktable_bridge.py`, and the XMP writer — which is why the scalar `subject` / `photo_type` fields stay

Land this issue before or alongside Stage 6 step 1 (region router extraction). The current 50/50 blend in `score_fusion.py` is a placeholder and should be deleted, not extended.

## Success Criteria

- Images with multi-label Subject (e.g. `person` + `pet`) route through both sub-score paths and the blended score is closer to user expectation than the argmax-only score
- Images with multi-label Photo Type (e.g. `portrait` + `landscape`) receive a blended aesthetic weight vector
- Darktable shows multiple `photon|subject|*` or `photon|type|*` tags on ambiguous images; user tag-removal corrections feed [#66](#66) per axis
- Argmax-only consumers (legacy code reading `GenreResult.subject` / `.photo_type`) continue to work unchanged

## Backward Compatibility

- Scalar `subject` and `photo_type` fields on `GenreResult` remain — they are the argmax of `top_subjects[0]` and `top_photo_types[0]`
- `FusionResult.as_flat_dict()` continues to return the same flat keys
- Database migration is additive (two new JSON columns); existing `subject` / `photo_type` columns unchanged
- XMP gains new sequences; existing `photon:Subject` / `photon:PhotoType` scalar fields preserved
