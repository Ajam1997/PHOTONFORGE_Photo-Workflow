## Bug

Pressing the **Stop** button during the scan step does not stop processing promptly. Stop was pressed at file 8, but the plugin continued processing until file 100.

## Root Cause

Two contributing factors in lua/photonforge/runner.lua:

1. **No abort check inside line-processing loop** (lines 225-243): The inner for line in new_data:gmatch(...) loop processes ALL buffered log output in a single pass without ever checking M.abort. Since dt.control.sleep(500) yields for 500ms between polls, a fast step like scan can buffer hundreds of lines of output. All of those lines get processed and displayed before the next while not M.abort check at the top of the loop.

2. **Windows process kill race**: Even after taskkill /F /PID terminates the Python process, output already flushed to the log file is still consumed by the next poll iteration.

## Expected Behavior

Processing should stop within 1-2 files of pressing the Stop button.

## Suggested Fix

- Check M.abort inside the line-processing for loop and break out immediately
- After the while loop exits on abort, skip processing any remaining buffered log output

## Repro

1. Configure scan with a folder containing 100+ files
2. Run the pipeline with scan enabled
3. Press Stop around file 8
4. Observe log continues to file ~100

## Environment

- Darktable 5.4.1 on Windows 11
- Lua plugin in lua/photonforge/
